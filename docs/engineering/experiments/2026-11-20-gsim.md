# gsim instead of Verilator for Wally (2026-11-20)

Whether [gsim](https://github.com/OpenXiangShan/gsim) (the RTL simulator of XiangShan, which compiles a FIRRTL design into C++) simulates Wally faster than
Verilator, for the long runs (Linux, SPEC checkpoints).  Conclusion: it is cycle-exact on ACT and faster than Verilator with wsim's default flags, but only 4-7 %
faster than Verilator with profile-guided optimization (`wsim --pgo`, which this experiment led to).  Not worth a second simulation flow for now; the code is kept
in `sim/gsim/` of the branch `gsim`, unmaintained.

## Flow

gsim reads FIRRTL (CHIRRTL), and Wally is SystemVerilog, so `sim/gsim/yosys2firrtl.py` (our own) turns Yosys's JSON netlist of Wally into CHIRRTL:

- Yosys reads the design (`Makefile`, `CONFIG=`), skips `memory_collect` (its `INIT` parameter is too wide for a 128 MiB RAM) and keeps read ports without `memory_dff`.
- The exporter writes the nodes in topological order, flops as `reg` plus multiplexers, memories as `cmem` with `infer` read ports and `write mport`.  A memory with
  partial (byte) writes becomes one wide memory written by read-modify-write, 11 % faster than one memory per byte (`--split` keeps that form).
- `sim/gsim/src/` replaces a few RTL files: the integer and floating-point register files written on the rising edge with a bypass, `ram1p1rwbe` and `rom1p1r` with
  `logic` storage and no `$readmemh` (a `bit` array of 128 MiB exceeds Yosys's `WIDTH_LIMIT`).  The SPI controller is left out (it has a falling-edge flop).
- `gsimtop.sv` is the top: it exposes registered M-stage monitor ports (after a step, gsim's combinational nodes are stale; only flops read consistently).
- `tb.cpp` is one harness for gsim (`-DGSIM`) and for Verilator built from the same top (`make verilator`), so the two are compared on identical RTL: it loads the
  ELF and detects the store to `tohost` as `testbench.sv` does.
- `docker-run.sh` runs the build in the `xiangshan-devtest` image (gsim, clang 19).  Generating the C++ for Wally takes under a second (XiangShan needs 67-160 GB).

Not done: UART output (no `$display`; would need a decoder of `UARTSout` in the harness), a loadable boot ROM (needed for Linux and checkpoints: the ROM is a
constant), the Linux/checkpoint harness (bootmem, `mtime` forcing, HPM dump).

## Results

ACT: rv32gc 1479/1479 and rv64gc 1741/1741 pass, with the same instructions retired as Verilator; gsim's cycle count is Verilator's + 1 in every test (a constant
offset of the harness), so the model is cycle-exact.

Speed, gsim against Verilator on the same top, Verilator with wsim's flags (-O2):

| workload | gsim / Verilator |
|---|---|
| ACT rv32gc | 1.56x |
| ACT rv64gc | 1.94x |
| tests idle in WFI | about 10x |
| CoreMark rv32 | 1.22x |
| CoreMark rv64 | 1.36x |

With profile-guided optimization on both sides (CoreMark rv32, simulated cycles per second):

| model | cycles/s |
|---|---|
| Verilator, -O2 | 312 k |
| Verilator, GCC PGO | 403 k (+29 %) |
| gsim, clang PGO | 420 k |
| gsim, clang PGO + BOLT | 432 k |

Best against best: 1.07x.  rv64 with PGO was not measured (without PGO gsim's advantage was larger on rv64).  Tuning: `-march=native` +3 %; supernode size 15 is
the best (5 the same, 35 and 80 worse); Yosys's `wreduce`, `peepopt` and `muxpack` gain nothing.

For comparison, XiangShan reports gsim with BOLT at about 2x Verilator -O3 and 1.5x the best Verilator on its own core, and there gsim is not cycle-exact (-0.84 %).

The PGO measurement made Verilator's own PGO a feature of `wsim` (`--pgo`; used by `regression-wally` and every buildroot build): CoreMark rv32 28 % faster, ACT rv64
22-24 %, a Linux boot 16-19 %.
